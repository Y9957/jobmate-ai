# 평가

검증 단계(원문 대조, 의미 검증)가 **근거 없는 충족 판정을 실제로 줄이는지**를 측정한다.

## 무엇을 재는가

공고 파싱 품질이 섞이지 않도록, 각 케이스의 요구조건 목록은 **정답으로 고정**하고 매칭·검증 단계만 평가한다.
세 시스템은 **같은 모델, 같은 프롬프트**를 쓰고 검증 유무만 다르다.

| 시스템 | 설명 |
|---|---|
| A. 검증 없음 | 매칭 1회 결과를 그대로 신뢰 (일반적인 "LLM에 물어보고 끝" 방식) |
| B. 원문 대조 | 인용문이 이력서에 없으면 피드백과 함께 재시도, 3회 실패 시 근거 부족으로 강등 |
| C. 원문 대조 + 의미 검증 | B에 더해, 인용문이 요구조건을 실제로 뒷받침하는지 LLM이 한 번 더 확인 |

## 지표

시스템의 `insufficient`(근거 부족)는 미충족으로 센다. 확인되지 않으면 충족이 아니다.

| 지표 | 정의 | 방향 |
|---|---|---|
| **근거 없는 충족 판정** | 충족으로 판정한 것 중, 인용문이 라벨된 근거 줄이 아닌 비율 (오탐 + 엉뚱한 근거 + 지어낸 인용) | 낮을수록 좋음 (핵심 지표) |
| 지어낸 인용 | 충족으로 판정한 것 중, 인용문이 이력서에 아예 없는 비율 | 낮을수록 좋음 |
| 잘못된 충족(오탐) | 정답이 미충족인 항목을 충족으로 판정한 비율 | 낮을수록 좋음 |
| 충족 재현율 | 정답이 충족인 항목을 올바른 근거와 함께 충족으로 판정한 비율 | 높을수록 좋음 (검증이 너무 엄격해지는 비용을 본다) |
| 판정 정확도 | 인용문은 보지 않고 충족/미충족만 맞춘 비율 | 높을수록 좋음 |

## 데이터

- `cases/*.json` — 가상 이력서 6개 × 공고 2개 = 12케이스, 요구조건 69개(충족 40 / 미충족 29)
- 함정 유형: 그대로 언급(direct), 다른 표현(paraphrase), 없음(absent), 비슷하지만 다른 것(adjacent_trap: Java↔JavaScript, Tableau↔Power BI, ECS↔Kubernetes, ADsP↔SQLD 등),
  그럴듯한 문장(tempting_quote), 경력 연수(years), 학위(degree), 정보 없음(no_info)
- 라벨 규칙: [LABELING.md](LABELING.md). 근거 줄이 실제 이력서에 있는지 등 데이터 무결성은 `backend/tests/test_eval_cases.py`가 매번 확인한다.

## 실행

```bash
cd backend
python -m app.evals.run                 # 세 시스템 모두, 설정된 모델로
python -m app.evals.run --limit 2       # 앞 2케이스만 (빠른 점검)
```

결과는 `results/<시각>_<모델>_<프롬프트버전>.json`(항목별 상세)과 `.md`(요약 표)로 저장된다.

## 한계

- 케이스 12개·요구조건 69개는 작은 데이터다. 수치 차이 1~2건은 우연일 수 있다.
- 라벨은 1차로 Claude가 규칙에 따라 작성했고, 저장소 소유자가 검토한다.
- temperature 0으로 1회 실행한 결과다. 로컬 모델도 GPU 연산 특성상 실행마다 약간 달라질 수 있다.
