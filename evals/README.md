# 평가

검증 단계(원문 대조, 의미 검증)가 **근거 없는 충족 판정을 실제로 줄이는지**를 측정한다.

## 결론 먼저

| 데이터 | 결과 | 해석 |
|---|---|---|
| **test v5** (보지 않은 데이터, 1회 실행) | 검증 없음도 판정 정확도 100%, 오탐 0%. 검증 단계는 **차이를 만들지 못했고** LLM 호출만 2배 | 프롬프트 정책을 다듬은 뒤의 8B 모델은 이 데이터에서 검증이 잡을 오류를 거의 내지 않았다 |
| dev v5 (조정에 쓴 데이터) | 근거 없는 충족 10.3% → **0%**, 지어낸 인용 5.1% → **0%**, 오탐 7.4% → **0%** | 모델이 틀릴 때는 검증이 그 오류를 전부 걸러냈다. 단, 조정에 쓴 데이터라 낙관적인 수치다 |
| test v3 (당시 보지 않은 데이터) | 의미 검증으로 오탐 11.8% → 5.9%, 그러나 재시도 결함으로 재현율 91% → 74% | 결함을 찾아 v4에서 고침 → 이 데이터는 이후 dev로 이동 |

**지금 말할 수 있는 것**
- 검증은 **안전장치**로는 확실히 동작한다: 지어낸 인용은 원문 대조를 통과할 수 없고(구조상 보장), 남이 한 일·엉뚱한 근거는 의미 검증이 걸러낸 사례가 dev에 여러 건 있다.
- 하지만 **보지 않은 test에서 "검증이 정확도를 올린다"는 효과는 아직 측정되지 않았다.** 이 결론은 test v5 기준이다.
- 오히려 가장 큰 개선은 **검증이 드러낸 오류를 보고 프롬프트 정책을 고친 것**(v4 재시도 피드백, v5 기술 목록·경력 직무 규칙)에서 나왔다.

## 무엇을 재는가

공고 파싱 품질이 섞이지 않도록, 각 케이스의 요구조건 목록은 **정답으로 고정**하고 매칭·검증 단계만 평가한다.
파이프라인을 케이스마다 **한 번** 실행하고, 같은 실행의 단계별 결과를 비교한다(v4부터). 모델 출력이 실행마다 달라지는 영향이 비교에 섞이지 않는다.

| 시스템 | 어느 시점의 결과인가 |
|---|---|
| A. 검증 없음 | 첫 매칭 직후 — "LLM에 한 번 물어보고 끝" |
| B. 원문 대조 | 원문 대조와 재시도(최대 3회)를 마친 뒤. 인용문 앞뒤에 붙은 제목·날짜는 코드로 떼어냄 |
| C. 원문 대조 + 의미 검증 | B 뒤에, 인용문과 그 이력서 줄이 요구조건을 실제로 뒷받침하는지 LLM이 한 번 더 확인 |

## 지표

시스템의 `insufficient`(근거 부족)는 미충족으로 센다. 확인되지 않으면 충족이 아니다.

| 지표 | 정의 | 방향 |
|---|---|---|
| **근거 없는 충족 판정** | 충족으로 판정한 것 중, 인용문이 라벨된 근거 줄이 아닌 비율 (오탐 + 엉뚱한 근거 + 지어낸 인용) | 낮을수록 좋음 (핵심 지표) |
| 지어낸 인용 | 충족으로 판정한 것 중, 인용문이 이력서에 아예 없는 비율 | 낮을수록 좋음 |
| 잘못된 충족(오탐) | 정답이 미충족인 항목을 충족으로 판정한 비율 | 낮을수록 좋음 |
| 충족 재현율 | 정답이 충족인 항목을 올바른 근거와 함께 충족으로 판정한 비율 | 높을수록 좋음 (검증이 너무 엄격해지는 비용) |
| 판정 정확도 | 인용문은 보지 않고 충족/미충족만 맞춘 비율 | 높을수록 좋음 |
